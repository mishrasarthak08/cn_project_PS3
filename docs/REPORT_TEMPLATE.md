## 7. Packet Capture & Protocol Analysis (Task G)

- **Capture Tool:** `scripts/capture-packets.sh <seconds> <outfile.pcap>`.
- **Observed Protocol Flow:**
  1. **DNS Query & Response:** UDP `ephemeral_port -> 53` (`app.team1.test` -> `10.7.11.189`).
  2. **TCP 3-Way Handshake:** TCP `SYN -> SYN-ACK -> ACK` to `10.7.11.189:8443`.
  3. **TLS 1.3 Handshake:** `ClientHello` (with SNI `app.team1.test`) followed by `ServerHello` (Cipher `TLS_AES_256_GCM_SHA384`, Key Share `X25519MLKEM768`).
  4. **ALPN Negotiation:** Client and Edge negotiate `h2` (HTTP/2 binary framing).
  5. **Encrypted Application Data:** Encrypted TLS records over port 8443.
  6. **Internal Proxying:** Nginx edge proxies request over cleartext HTTP to backend port 3001 or 3002.
- **Wireshark Display Filters:**
  - DNS queries: `dns`
  - TCP handshake: `tcp.flags.syn == 1`
  - TLS handshake: `tls.handshake`
  - Edge traffic: `tcp.port == 8443`

## 8. Failure Scenarios & Resilience Demonstration

The system includes built-in scripts to simulate real-world failure modes and demonstrate network fault isolation:

### Scenario 1: Wrong DNS Resolver on Client
- **Execution:** `bin/failure-demo wrong-resolver break`
- **Observation:** `dig` and `curl` fail immediately with "Could not resolve host: app.team1.test", but `ping 10.7.11.189` succeeds.
- **Root Cause & Concept:** Demonstrates that the Application/Name layer is decoupled from the Network/IP routing layer. IP connectivity remains intact even when name resolution is unreachable.
- **Rollback:** `bin/failure-demo wrong-resolver rollback`

### Scenario 2: DNS Points to Incorrect IP
- **Execution:** `bin/failure-demo wrong-dns-record break` (points `app.team1.test` to `192.0.2.99`)
- **Observation:** `dig app.team1.test` succeeds with `192.0.2.99`, but `curl` times out.
- **Root Cause & Concept:** DNS is a distributed directory service without awareness of host liveness. A valid DNS response does not guarantee reachability or open ports.
- **Rollback:** `bin/failure-demo wrong-dns-record rollback`

### Scenario 3: Single Backend Node Outage (Backend A Fails)
- **Execution:** Shitanshu executes `./macs/mac3-shitanshu/stop.sh`
- **Observation:** `curl https://app.team1.test:8443/api/status` continues to succeed without downtime; 100% of responses return from `{"backend": "B", "owner": "Shane"}`.
- **Root Cause & Concept:** Nginx passive health monitoring (`max_fails=1`, `fail_timeout=10s`, and `proxy_next_upstream error timeout http_502`) automatically isolates the faulty node and reroutes requests to healthy Backend B.
- **Rollback:** Shitanshu executes `./macs/mac3-shitanshu/start.sh`

### Scenario 4: Total Backend Cluster Outage (Both Nodes Down)
- **Observation:** DNS resolves, TCP connects, and TLS completes successfully, but Nginx returns `HTTP/2 502 Bad Gateway`.
- **Root Cause & Concept:** Demonstrates reverse-proxy semantics: the edge server remains fully healthy and terminates TLS, but reports an upstream gateway failure when no backend is available.
